# Decision log

Status: **Approved** = owner approved. **Assumed** = default chosen by the architect; the owner was unsure and delegated.
Assumed decisions can be revisited, but changing them after data exists costs more.

| D17 | Admin passwords hashed with PBKDF2-HMAC-SHA256 (210,000 iterations, per-password salt) from the .NET base library, stored as `pbkdf2-sha256$iterations$salt$hash` | Assumed | Follows D7 (no ASP.NET Core Identity store). The iteration count travels with each hash, so it can be raised later without invalidating existing passwords |
| D18 | ~~Admin sign-in is password-only for now~~ — superseded by D28 | Superseded | TOTP MFA is now mandatory and enforced by audience-separated tokens |
| D19 | The latest review decision is stored on the listing (`review_note`, `reviewed_at`, `reviewed_by_admin_id`, migration V0004); the audit log keeps the full history | Assumed | The owner's screens need the current reason without reading audit rows |
| D20 | A listing an admin adds by hand goes live immediately only if that admin also holds `listings.review`; otherwise it joins the review queue | Assumed | Otherwise "add listings manually" would quietly include the power to publish |
| D21 | After a decision, the admin site asks the public site to refresh the affected pages (`POST /api/revalidate`, shared secret). Without the secret the public site falls back to its 60-second revalidation | Assumed | Keeps approvals near-instant without making every public page uncached |
| D22 | Public URLs keep the locality-first scheme `/{city}/{locality}/{category}/{slug}` and the two-level taxonomy. The live site's category-first URLs (`/food/restaurants/barbeque-and-grill/kphb/{business}`) are served by 301 redirects instead of being adopted | Approved | Adopting them would need a migration relaxing `categories_two_levels` and `listing_categories`, a three-level taxonomy re-seed, and would drop the city segment, breaking every URL when a second city is added. Redirects keep the existing search equity without any of that |
| D23 | Four subscription tiers: Free ₹0, Basic ₹699, Advanced ₹6999, Premium ₹36999, sold on SEO, website and social-media work rather than photo counts | Approved | Taken from the owner's prototype, superseding D9. **Still unconfirmed:** the photo/video allowance for each tier, and whether paid Basic grants a verified badge — the earlier requirement that a paid plan must never auto-grant one has not been withdrawn. Both must be settled before media or billing work |
| D24 | Owner onboarding collects name, business name, email, locality and primary category, then creates the user profile, business, ownership row and first **draft** listing in one transaction | Approved | `listings` requires `locality_id`, `location`, `phone_primary` and a primary category. Collecting locality and category means the first listing is built from real data — location from the locality centre, phone from the verified number — instead of inventing values or relaxing the schema |
| D25 | Header navigation shows the real top-level categories (up to seven on the bar, the rest reachable through an "All categories" panel), not the reference site's wording ("Food", "Stays", "Health & Wellness") | Approved | The reference's seven headings match only two of the seventeen real categories. Renaming them would mean a migration, a re-seed of 134 sub-categories and changed slugs; a frontend-only display grouping would create a second taxonomy to keep in step. Real data, no hardcoded names |
| D26 | The owner dashboard lives at `/account/*` inside `apps/main-website`, not in a fourth Next.js application | Approved | The owner's live site serves its business-owner panel from a path (`/BO/Dashboard`) on one domain, so a path is proven sufficient. A separate app would duplicate authentication, the session cookies and the design system |
| D27 | `PUT /api/v1/me/profile` lets an owner change their own name and email after registration | Assumed | Onboarding's `name IS NULL` guard (D24) stops a repeated registration overwriting a profile, but it also left the owner no way to fix a typo in their own name. No migration: `users.name` and `users.email` already exist. The verified phone is not editable, since changing it needs re-verification |
| D28 | Admin MFA is mandatory TOTP, enforced by issuing the password step a token on a *different audience* so it cannot satisfy the admin policy. The session and refresh token are created only by the MFA step | Approved | A check inside a handler can be forgotten or bypassed by a new route; an audience the scheme rejects cannot. `admin_sessions.last_mfa_at` records completion and refresh carries it forward |
| D29 | TOTP and Base32 are hand-written against RFC 6238 and RFC 4648 rather than taken from a package | Assumed | Follows D7 and D17, which already hand-write password hashing instead of using ASP.NET Core Identity. Both are covered by the specifications' own published test vectors |
| D30 | The TOTP secret is encrypted with AES-256-GCM under `Auth:TotpEncryptionKey`, not protected by ASP.NET Core Data Protection | Approved | Matches the existing `Auth:JwtSigningKey` / `Auth:OtpHmacKey` pattern and needs no key-ring infrastructure. It adds one production secret, and rotating it requires every admin to re-enroll |
| D41 | The database moves from PostgreSQL to **Microsoft SQL Server / Azure SQL Database**, and PostgreSQL support is not retained | Approved by the owner 2026-10-20 | The company's Azure estate is SQL Server, so the platform must run there. Dual support was considered and rejected: without an ORM (D6), approximately 145 raw queries would need to be maintained in two dialects. The PostgreSQL migrations remain in `database/migrations/` as historical records and must never be executed again. The active migration path is `database/sqlserver/migrations/`. |
| D42 | pg_trgm's typo tolerance is reproduced with a **stored trigram table**, not with SOUNDEX/DIFFERENCE | Approved by the owner 2026-10-20 | SQL Server has no trigram support. SOUNDEX matches by sound and would lose exactly what this search is for: "patan" finding Patancheru is verified behaviour on a site whose users type Hyderabad place names from memory. The table stores each name's trigrams and the similarity is pg_trgm's own formula, shared / (mine + theirs - shared). Measured on real names: patan→Patancheru 0.417, gachi→Gachibowli 0.417, madapur→Madhapur 0.545, and 0 for everything unrelated |
| D43 | PostgreSQL's weighted `tsvector` column is replaced by a SQL Server full-text index over `name` and `description`, with the weighting applied in the query | Assumed | SQL Server's full-text index covers real columns, so the generated column disappears. "Name outranks description" becomes two `CONTAINSTABLE` calls whose ranks are combined, which keeps the behaviour where it can be read rather than hidden in a stored column |
| D44 | `ON DELETE CASCADE` from `users` was dropped on `reviews` and `favourites` | Assumed | SQL Server refuses a table with two cascade paths into it ("may cause cycles or multiple cascade paths"). Nothing in the application deletes a user account -- it marks one `deleted` -- so the cascade was never exercised. The same applies to `admin_user_roles`, which has two foreign keys to `admin_users` |
| D39 | Platform administration lives on `/api/v1/super-admin` behind a **fifth token audience** (`super-admin`), issued alongside the admin token only to an account holding `admins.manage` | Approved by the existing design | `AdminPermissions` already said "super-admin work belongs on /api/v1/super-admin with its own token audience" and `AdminAccess.Authorize` already refused super-admin permissions on the admin surface. This implements what that rule assumed: an ordinary administrator's token is refused by the scheme before a handler runs, and a super-admin token is refused by `/api/v1/admin` in the same way |
| D40 | The super-admin site cannot create an admin account or reset anyone's password | Assumed | Both need a credential delivered to a person, and no email provider is configured. `create-admin` on the command line stays the only way to make an account. Clearing someone's **authenticator** is offered, because it removes a factor rather than granting a way in: the password is untouched and the next sign-in walks the setup again |
| D35 | Suspending and reinstating a live listing is gated on the existing `listings.review` permission, and the reason is stored in `review_note` | Assumed | An account trusted to publish a listing is the one trusted to unpublish it, so no new permission was invented. Reusing `review_note` means the owner sees why on the screens that already read it |
| D36 | Abuse reports (V0009) may be sent without an account, and are rate-limited per IP address (20 a day, 3 per subject) | Assumed | The people most likely to spot a fake listing are the customers it tried to catch; requiring an account would mean most problems are never reported. The limits are counted in the database, and both refusals answer the same way so repeating a request cannot reveal which was hit |
| D37 | Closing a report never changes the listing or review it is about | Assumed | Suspending a listing and rejecting a review are separate, audited actions with their own checks. Keeping them apart means "the queue is empty" never silently means "ten listings were taken down" |
| D38 | Favourites are private: no public count, and no owner is told who saved their listing | Assumed | A count would be worth faking and nothing in the product needs it. A favourite whose listing stops being live is kept but marked unavailable rather than removed |
| D32 | Plans live in a `plans` table with the media allowances as columns, and `media_limits_confirmed` marks them provisional until the owner settles them (V0008) | Assumed | D23 approved the four tiers and their prices but not the allowances. Rows rather than C# constants mean the owner's answer is an UPDATE, not a deploy; the flag lets every screen say the numbers are not final instead of implying they are. The reference seed deliberately never overwrites an allowance that has been confirmed |
| D33 | Listing media is stored in Azure Blob Storage behind one `IMediaStorage` interface, in a **public-read** container, with no SAS tokens or signed URLs | Assumed | Every file in it is a photo on a public listing page, so there is nothing to keep private, and public blobs mean the browser loads them directly instead of streaming through the API. It does require the storage account to allow blob public access; `Media:PublicBaseUrl` puts a CDN or custom domain in front of it |
| D34 | A file's type is decided from its first bytes, never from the filename or the declared Content-Type, and the stored blob name is `listings/{id}/{kind}/{random}` with nothing of the uploaded name in it | Assumed | A `.jpg` beginning `MZ` is a Windows executable; accepting it would serve an executable from a business's own gallery. A random name also makes path traversal and one upload overwriting another impossible |
| D31 | `admin_users.totp_last_step` (V0005) records the step of the last accepted code | Assumed | Replay cannot be detected exactly from `last_mfa_at`: a code accepted from the next step, which the drift window allows, belongs to a later step than the completion time, leaving it replayable |
| D41 | Every notification is recorded in a `notifications` table (V0010) **before** it is sent, inside the transaction that caused it, and delivery happens after the commit. A delivery failure never fails the request that triggered it | Assumed | An enquiry that was recorded matters more than an email that went out, so sending cannot be allowed to roll back the enquiry. Writing the row first is what makes a failure visible: without it, an unconfigured provider or a dead API key would be a silent nothing, and the first person to notice would be an owner wondering why they never hear about their customers. The table is a log of attempts, not a queue; nothing retries from it yet |
| D42 | Email goes through one provider-agnostic `IEmailSender` (`ConsoleEmailSender` in Development, `UnconfiguredEmailSender` everywhere else), configured under `Email:`. **No provider adapter has been written**, because D14's choice of Resend is still unconfirmed | Assumed | Exactly the `ISmsSender` pattern (D7's "own building blocks" approach), so the notification code does not know which provider is behind it and a provider decision is one new class, not a rewrite. Nothing claims the integration works until a provider has actually been configured and tested |
| D45 | Payments go through one `IPaymentGateway` (`RazorpayGateway`, `UnconfiguredPaymentGateway`), configured under `Payments:`. A listing becomes Verified **only** through `Subscriptions.RecordVerifiedPaymentAsync`, which both callers reach after a signature check | **Needs the owner's confirmation of the provider** | The same seam as `ISmsSender` (D7) and `IEmailSender` (D42), so a change of provider is one class. S0009 already defaulted `subscription_payments.provider` to `razorpay`, and the adapter is written against Razorpay's documented contract — but **no account exists and no payment has been taken**, so the provider choice is still open and the integration is unverified. With nothing configured every paying route answers 503 and writes nothing; a key id without its secret counts as unconfigured, because a checkout that cannot be verified ends with a customer charged and no subscription |
| D46 | The webhook (`POST /api/v1/webhooks/razorpay`) is authenticated by its HMAC signature over the **raw** body, with no token and no authorization policy, and its idempotency is the unique index on (provider, webhook_event_id) | Assumed | A shared bearer token in a provider dashboard proves only who sent the request; an HMAC over the body also proves the body was not edited, which matters because the body carries the amount. Parsing before verifying would break the signature, so the endpoint reads the stream first and looks inside afterwards. The webhook exists because the browser is not a reliable messenger: a customer who closes the tab mid-payment would otherwise be charged with their listing still Free |
| D47 | A renewal extends from the existing `expires_at`, not from the day it is paid, and a lapsed period is closed to `expired` before a new one is opened | Assumed | Renewing a month early must not cost the owner that month. `subscriptions_one_active_idx` allows one active row per listing, so the lapsed row — whose status is still `active` until something says otherwise, even though the entitlements view has read it as expired all along — has to be closed first or the insert is refused |
